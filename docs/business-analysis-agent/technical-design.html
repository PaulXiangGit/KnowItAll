1. 产品定位与目标

KnowItAll 不是“会聊天的文档搜索”，而是一个围绕业务变更建立事实链路、执行多源分析、输出证据化结论的业务分析 Agent。

面向角色

产品经理、前端、后端、测试、数据、SRE、项目经理及技术负责人。

核心任务

需求评审、技术方案、影响面分析、故障排查、事故复盘、历史相似性检索。

输出标准

结论、影响对象、证据、时间/版本、置信度、不确定项和下一步动作。

目标场景

  1. 识别一个产品需求影响的前端页面、组件、路由与用户入口。
  2. 解释一个页面依赖的后端接口、协议、服务、数据库表与缓存。
  3. 分析接口或字段变更对产品能力、页面、埋点、实验和下游服务的影响。
  4. 查找与当前需求相似的历史需求、事故、技术方案和评审结论。
  5. 为排障推荐日志、指标、链路、发布记录、开关与配置的检查顺序。
  6. 审查需求/技术方案是否缺失关键字段、状态流、权限、异常态、埋点、监控或灰度策略。

非目标：首期不替代 Jira、Git、监控等源系统，不把模型推断写回为事实，不在无审批时执行生产变更，也不承诺仅凭文档回答所有代码级问题。

2. 设计原则

关键约束：RAG 只负责召回非结构化上下文，不作为唯一数据底座。业务实体、依赖关系、版本事实、权限与可追溯链路必须由可查询、可约束、可审计的数据结构承载。

事实与文本分离

“接口 A 在版本 V 包含字段 F”是版本事实；“方案文档讨论了字段 F”是文本证据。两者存储、更新和置信度不同。

来源优先于结论

任何高影响结论都能回到源系统、版本、文件路径、行号、文档段落、查询时间或观测窗口。

时间是一等公民

关系和属性均支持 valid_from/valid_to、采集时间和版本，避免拿当前事实解释历史事故。

确定性查询优先

精确 ID、字段、依赖和版本先走结构化/全文/图查询；语义模糊问题再用向量召回和模型推理。

权限随数据传播

检索结果取调用者权限交集；派生实体、切片、向量和答案继承源数据 ACL 与敏感级别。

可替换基础设施

通过 Storage Port、Connector SDK、Tool Protocol 隔离厂商能力，默认发行版简单，规模化部署可平滑替换。

4. 数据底座与技术选型

建议采用“逻辑多存储、默认少组件”的策略：能力上完整覆盖，本地开发默认使用 PostgreSQL + 本地文件存储；需要完整检索时增加 OpenSearch；生产环境可以选择付费云对象存储，也可以部署开源、自托管的 S3 兼容实现。

4.2 推荐选型矩阵

能力默认开源发行版规模化选项建议与取舍
关系数据库PostgreSQL 16+云托管 PostgreSQL推荐。生态成熟，可承载 JSONB、行级安全、递归 CTE 和 pgvector。
图关系PostgreSQL 邻接表（nodes/edges）ArangoDB / Neo4j / MemgraphMVP 用关系图减少组件；当 3+ 跳遍历 p95、图规模或图算法成为瓶颈时迁移。图层必须通过统一接口访问。

向量索引pgvectorQdrant / Milvus首期与元数据事务靠近；向量超千万、QPS 或多向量检索需求上升后拆分。所有结果仍回查 ACL。
对象存储本地文件系统TOS / S3 / OSS / COS；SeaweedFS / Garage / Ceph RGW通过 ObjectStore Port 保存不可变原件与派生物；数据库只保存 URI、hash、版本与 ACL，不绑定具体产品。

建议定案：“Local Profile”使用 PostgreSQL + pgvector + Redis + 本地文件对象存储；社区完整 Profile 可增加 OpenSearch 和用户选择的 S3 兼容存储；“Scale Profile”可增加 ArangoDB/Neo4j、Qdrant 和 Kafka。所有 Profile 共享同一领域模型和 Storage/ObjectStore Port。

4.3 何时需要专用图数据库

  • 线上分析频繁执行 4—8 跳、双向、带路径约束的遍历；
  • 边数量达到数亿，关系查询 p95 无法通过索引和预计算满足目标；
  • 需要中心性、社区发现、最短路径等图算法；
  • 图谱探索成为核心交互，而非回答生成的辅助能力。

4.4 ArangoDB Community 可行性评估

结论：可以作为 KnowItAll 的图关系存储，但建议定位为可选 Graph Adapter，而不是开源默认发行版的强依赖。

维度判断对 KnowItAll 的含义
图模型适合Vertex/Edge Document 可自然表达带属性、版本和证据引用的实体关系；一条边可保存 valid_from、valid_to、confidence 和 evidence_ids。
查询能力适合AQL 支持定深/变深遍历、DFS/BFS/加权遍历、剪枝、最短路径与路径枚举，可覆盖影响面、上下游依赖和证据路径查询。
多模型有价值Document 与 Graph 共用 AQL，便于把实体元数据和边放在同一引擎；但 PostgreSQL 仍是租户、任务、ACL、审计等事务事实的主库。
全文能力可用但不替代ArangoSearch 支持 BM25、精确/前缀/模糊等查询；为保持字段检索扩展性和存储可替换性，默认仍由 Search Port 对接 OpenSearch。
事务边界需约束Community 集群中的多 collection ACID 能力存在版本/功能边界；图写入采用幂等事件和最终一致，不设计跨 PostgreSQL、ArangoDB 的分布式事务。
许可证默认发行风险3.12 起源码采用 BSL 1.1；Community 预编译软件另受 Community License 约束。官方协议限定内部业务使用、聚合数据集低于 100GB，并限制转让、再分发或以独立方式提供。不能把“Community”直接等同于 OSI 开源。
一键部署可选安装KnowItAll 仓库可提供 adapter、配置和用户自备镜像的部署说明；是否可直接捆绑/再分发镜像应由项目维护者做许可证审查，不能仅凭技术方案认定。

建议的集成边界

  • 实现 GraphPort：upsertNode、upsertEdge、closeRevision、neighbors、paths、impact 和 subgraph；Agent 不直接生成 AQL。
  • 使用独立 database/collection 隔离租户或在所有文档中强制携带 tenant_id，并由服务端编译查询条件；不可依赖模型补充租户过滤。
  • 顶点 collection 按稳定实体类型或统一 entities 建模，边按关系域拆分；具体拆分由基准测试决定，领域层不暴露 collection 名。
  • PostgreSQL outbox 驱动 ArangoDB 幂等写入，边使用确定性 key；记录 knowledge_revision，支持重放、核对和全量重建。
  • 版本选择和许可证校验进入发布清单；商业生产使用前重新核对当时适用条款，并保留 PostgreSQL/其他图实现的迁移出口。

核对依据（访问于 2026-10-11）：ArangoDB 3.12 Community Edition 功能说明、ArangoDB Community Edition License Agreement、ArangoDB 许可证变更说明。许可证结论需由法律顾问确认，本节不构成法律意见。

4.5 对象存储部署与成本策略

结论：生产部署不等于必须购买云对象存储。KnowItAll 将对象存储抽象为 ObjectStore Port。用户可以在运维成本、可用性和直接费用之间选择：本地文件系统与开源自托管方案没有软件授权费，但仍需承担服务器、磁盘、备份和运维成本；TOS、AWS S3、阿里云 OSS、腾讯云 COS 等托管服务通常按容量、请求和流量计费，但可减少基础设施运维。

方案软件/服务费用运维责任推荐场景
LocalObjectStore（本地文件系统）无软件授权费自行处理磁盘、备份、扩容和高可用本地开发、Demo、单机和小团队部署
SeaweedFS开源，自托管资源另计自行部署、监控、备份和升级；提供 S3 API希望保持开源一键部署且规模中小的私有化环境
Garage开源，自托管资源另计自行维护分布式节点并评估 AGPLv3 合规资源有限、需要轻量分布式 S3 兼容存储
Ceph RGW开源，自托管资源另计部署和运维复杂度较高已有 Ceph 能力或需要大型、高可用集群
TOS / AWS S3 / OSS / COS通常按存储、请求、流量等计费云厂商负责底层可用性，应用负责权限、生命周期和成本治理希望降低运维投入的正式生产环境

开源发行版默认启用 local 后端，确保不购买云服务也能启动；可选的 s3-compatible 适配器统一支持自托管存储与兼容 S3 协议的云服务。TOS、OSS、COS 若存在签名、区域或专有能力差异，则在统一 Port 后增加薄适配器。MinIO 不再作为默认依赖：已有部署可以继续通过兼容适配器接入，但新安装不依赖其官方预构建镜像。

建议定案：本地与 Lite Profile 使用 LocalObjectStore；开源私有化 Profile 优先提供可选 SeaweedFS Compose；云生产环境由部署方选择 TOS/S3/OSS/COS。任何后端都不得绕过统一的业务线标签、ACL、内容哈希、审计和生命周期策略。

4.6 默认应用与 Agent 中间件

默认技术栈：Python 3.12 + FastAPI + LangGraph。FastAPI 是对外服务与安全边界，LangGraph 是进程内 Agent 编排引擎；领域服务、检索和存储通过 Port/Adapter 调用，不把业务规则写死在 Graph Node 中。
组件默认职责边界
FastAPIREST API、SSE 流式事件、请求校验、依赖注入、OIDC 身份上下文、租户/业务线作用域、限流和 OpenAPI不承担长时工作流状态，不直接拼接底层查询，不在路由函数中实现 Agent 推理
LangGraph有状态工作流、条件路由、并行工具节点、重试、checkpoint、暂停/恢复及 human-in-the-loop不作为事实库或业务记忆库；Graph State 仅保存运行所需的原始状态和引用
PydanticAPI DTO、Graph State、QueryPlan、EvidenceItem、Tool I/O 的 Schema 与校验领域实体持久化模型与外部 DTO 分离
Uvicorn开发和单实例 ASGI Server生产多副本由容器编排和反向代理处理
Worker连接器同步、解析、Embedding、索引重建和长时后台任务不阻塞 FastAPI 请求进程；首期使用 Redis Streams，后续可替换 Kafka

设计依据：LangGraph 官方文档将 State、持久化 checkpoint、节点级重试和 interrupt() 作为有状态 Agent 与人工介入的核心原语；FastAPI 提供异步 API 与流式响应能力。参考：LangGraph Overview、LangGraph Interrupts、FastAPI Stream Data。

实体采用 Identity + Revision 双层模型：稳定 ID 表示同一业务对象，Revision 表示某个时间点的属性快照。关系同样版本化，删除使用闭合 valid_to，不直接抹除历史。

5.4 业务线作用域模型

业务线不是自由文本标签，而是受治理的实体 BusinessLine。它具有稳定编码、名称、别名、父子层级、负责人、状态和可见范围。实体、文档切片、代码仓库/目录、图节点/边、会话及记忆均可关联一个或多个业务线。

  • 多标签：共享服务、公共组件和跨域需求允许多个 business_line_ids，并记录主业务线与关联业务线。
  • 标签来源：EXPLICIT（用户/管理员指定）、RULE（仓库、项目或目录映射）、INHERITED（从父对象传播）、INFERRED（模型推断）。
  • 可追溯：标签绑定包含来源、置信度、证据、创建者、时间和版本；推断结果不能覆盖人工确认标签。
  • 继承规则：Requirement 可从 Jira Project 继承，代码实体可从 repo/path 规则继承，文档切片默认继承文档标签；发生冲突时保留多标签并进入治理队列。
  • 权限关系：业务线负责缩小语义与记忆范围，ACL 决定用户是否能看。有效查询范围始终是 业务线作用域 ∩ 用户授权范围。

6.2 多索引写入策略

  • 先落原件：对象存储写不可变快照，生成 SHA-256；失败不推进 checkpoint。
  • 再落事实：关系库事务写实体、Revision、证据和 outbox；图、全文、向量、代码索引异步消费 outbox。
  • 最终一致：每条索引记录带 knowledge_revision。查询计划可要求最低 revision；索引延迟在答案中可见。
  • 可重建：派生索引都可由原件 + 关系库事实重放；Embedding 模型升级写新 namespace，不原地覆盖。
  • 删除传播：按 ACL 撤销或源删除事件关闭版本并删除派生索引，保留合规范围内的审计墓碑。

6.3 实体对齐与冲突

优先使用强标识（Jira Key、OpenAPI operationId、repo+symbol、catalog path），其次使用可解释规则，最后才由模型提出候选。冲突进入待确认队列；未经确认的合并不得改变稳定实体 ID。

6.4 业务线标签加工

显式源字段→项目/仓库规则→关系继承→分类模型补充→置信度与冲突校验→索引字段写入

所有存储适配器都必须支持业务线过滤：关系库使用关联表，图存储写入节点/边作用域，全文和向量索引写入可过滤 metadata，对象存储 manifest 与代码符号表保存标签。标签修正通过 outbox 传播到派生索引，并能够按 revision 重建。

6.5 新语言与框架的渐进式适配

新语言默认可接入，不要求每种语言从零开发完整 Plugin。代码接入拆分为通用 Git Connector、Tree-sitter Grammar、语言查询包、语义索引适配器和框架规则五层；不支持深度语义的语言自动降级为文件、全文和向量检索。

等级能力新增语言所需工作
L0 通用接入Git、Commit、Diff、文件、全文与向量检索无需语言 Plugin；按扩展名和内容识别
L1 语法结构类、函数、方法、import/export、基础调用表达式复用已有 Tree-sitter Grammar，增加声明式 Query Pack
L2 语义引用跨文件 definition/reference、类型和较准确调用关系接入 LSP、SCIP、LSIF 或语言原生编译器索引
L3 框架语义路由、ORM、消息、依赖注入、Agent 节点等业务关系增加 FastAPI、Spring、Next.js 等 Framework Rule/Plugin
L4 运行时验证实际调用、流量、错误和动态绑定接入 Trace、日志或运行时探针

维护版本化 GrammarRegistry，记录语言扩展名、Grammar 仓库与版本、许可证、Query Pack 版本、成熟度和测试语料。成熟度分为 CERTIFIED、VERIFIED、COMMUNITY、TEXT_ONLY。第三方 Grammar 必须锁定 commit/hash 并经过恶意输入、解析错误率和性能测试后才能进入默认发行版。

7. Agent 编排设计

默认使用 LangGraph（Python）实现可恢复的状态图，由 FastAPI 创建 Run、注入用户与业务线作用域、订阅执行事件并处理人工确认。领域逻辑放在独立 Service 中，LangGraph Node 只负责调用、状态转换和路由。

7.1 运行流程

问题与身份→业务线作用域解析→意图/风险识别→查询计划→工具并行执行→证据归一→冲突检测→结论合成→人工确认/输出
问题类型首选工具补充工具
精确字段/接口/错误码查询全文索引 + 结构化查询代码符号检索
影响面与依赖分析图遍历 + 版本过滤代码引用、运行时 Trace、RAG
历史相似问题向量 + BM25 混合召回元数据过滤、图邻域重排
需求完整性审查规则/Checklist + 结构化字段历史相似需求、LLM 批判审查
排障日志/指标/Trace 查询 + 发布/配置时间线依赖图、相似事故召回

7.2 Planner 与执行器

Planner 输出受 JSON Schema 约束的 QueryPlan，包含假设、时间范围、环境、实体锚点、工具步骤、预算和停止条件。Executor 只允许调用注册工具；每个工具返回统一 EvidenceItem[]，而不是自由文本。

{
  "intent": "CHANGE_IMPACT",
  "scope": {
    "business_lines": ["commerce-order"],
    "scope_source": "USER_EXPLICIT",
    "project": "commerce", "env": "prod", "as_of": "2026-10-11"
  },
  "anchors": [{"type": "API_FIELD", "value": "Order.discountAmount"}],
  "steps": [
    {"tool": "entity.resolve", "required": true},
    {"tool": "graph.traverse", "direction": "both", "max_hops": 4},
    {"tool": "code.references", "at_revision": "release/current"},
    {"tool": "search.hybrid", "filters": {"doc_type": ["requirement", "design"]}}
  ],
  "human_gate": "REQUIRED_IF_HIGH_RISK_OR_LOW_CONFIDENCE"
}

LangGraph 默认节点

resolve_scope→classify_intent→build_plan→execute_tools→normalize_evidence→detect_conflicts→score_confidence→human_gate→compose_answer
  • resolve_scope 必须先于任何记忆与知识检索，产出服务端验证过的 effective_scope。
  • execute_tools 可按计划并行执行只读工具，但每个结果必须携带 Evidence Envelope。
  • human_gate 使用 LangGraph interrupt() 暂停；FastAPI 确认接口以同一 thread_id/run_id 恢复。
  • 每个可重试节点声明显式 retry policy；副作用工具使用幂等键，避免 checkpoint 恢复后重复执行。

Graph State 最小字段

class AnalysisState(TypedDict):
    request_id: str
    thread_id: str
    user_context: UserContext
    question: str
    effective_scope: BusinessScope
    intent: AnalysisIntent | None
    plan: QueryPlan | None
    evidence: list[EvidenceItem]
    conflicts: list[EvidenceConflict]

Graph State 保存结构化原始数据或稳定 ID，不保存拼好的 Prompt、数据库连接、凭证和无限增长的完整文档。大结果写入对象存储/证据库，State 仅保存引用。Checkpoint 与业务事实分库分表，并配置 TTL。

7.3 工具与安全边界

  • 查询类工具默认只读，参数化查询，限制 hop、时间窗口、返回量和执行时间。
  • 源系统写入、创建工单、修改配置、触发发布均属于 Action Tool，必须显式授权并二次确认。
  • 模型不能直接拼接数据库 SQL、日志查询或 shell 执行；由服务端 DSL 编译和策略校验。
  • 模型输出中的实体必须经 resolver 绑定真实 ID；未绑定内容标记为“推测”。
  • 达到工具预算、证据不足或证据冲突时停止扩张检索，转为报告不确定性或请求人工确认。

7.4 记忆设计

会话短期记忆保存当前任务状态；用户偏好保存展示方式；经人工确认的知识修正进入治理工作流。对话内容不会自动晋升为组织事实，避免“聊天污染知识库”。

7.5 业务线感知的交互与记忆隔离

每一轮提问都有独立的业务线作用域。用户可以主动设置，系统也可以根据问题中的实体、项目、仓库、接口、历史选项和用户可访问业务线进行推断。UI 在输入框附近持续展示当前作用域，回答头部再次标明，避免用户误以为系统正在查询全部数据。

交互状态系统行为记忆检索行为
用户显式指定一个标签本轮采用该标签，优先级最高；校验用户权限只选择该业务线及获准公共域的历史记忆
用户显式指定多个标签进入跨业务线模式，UI 明示作用域列表按每条业务线分桶召回、配额平衡，再合并去重
系统高置信推断自动应用并展示“推断：订单业务线”，允许一键修改仅使用推断标签相关记忆，并记录推断证据
推断结果相近或低置信不静默选择；让用户确认候选标签，或在无历史记忆模式下继续确认前不注入业务线历史记忆
问题明确跨域建立临时多标签作用域，逐域检索并标注来源不把某一业务线记忆未经标注地带入另一业务线
用户本轮切换标签立即生成新的 Turn Scope，不修改此前消息的作用域重新检索新作用域记忆；旧作用域记忆不进入上下文

作用域解析优先级

  1. 本轮用户显式设置的标签；
  2. 问题中出现的强实体映射，例如 Jira Project、仓库、接口或页面的唯一归属；
  3. 当前会话上一轮已确认的标签，但只有在本轮没有切换信号时才继承；
  4. 分类模型根据文本和候选业务线推断；不得因为用户常用某业务线就忽略本轮明确实体。

记忆召回与写入

effective_scope = requested_business_lines
                  ∩ user_allowed_business_lines

memory_candidates = retrieve(
  conversation_id = current_conversation,
  business_line_ids OVERLAP effective_scope,
  memory_status = "ACTIVE",
  top_k = scoped_budget
)

context = rerank(memory_candidates, current_question)
          + explicitly_pinned_global_preferences
  • 每条长期/摘要记忆必须带 business_line_ids、scope_source、scope_confidence 和来源 Turn ID；没有标签的业务记忆默认不参与召回。
  • 全局记忆仅允许保存语言、输出格式等非业务偏好，需使用白名单；业务事实不能标成 global 绕过隔离。
  • 公共平台/基础设施记忆使用受治理的 shared 标签，并且只有与本轮问题语义相关、用户有权限时才加入。
  • 生成会话摘要时按业务线分别摘要；跨域对话生成多个分区摘要，不生成混合业务事实摘要。
  • 回答必须返回实际使用的业务线标签、标签来源、推断置信度以及记忆条数，支持用户发现和纠正串线。
降级原则：宁可少用记忆，也不要跨业务线误用记忆。标签不确定时可以继续做无历史记忆的知识查询，但必须显式提示作用域尚未确认。

8. 核心链路示例

8.1 接口字段变更影响分析

  1. 解析“删除 Order.discountAmount”并绑定 API schema 中的字段 Revision。
  2. 图谱反向遍历：字段 ← API ← 前端 API Client ← Component ← Page/Entry，同时遍历 Service → Method → Table、TrackingEvent、Experiment。
  3. 代码索引验证引用位置；Trace 验证生产环境实际调用；全文/向量召回相关需求与方案。
  4. 按“确定影响 / 可能影响 / 未发现影响”分组，列出路径、版本、证据与负责人。
  5. 若涉及支付、权限或数据破坏，强制人工确认；生成测试建议和兼容方案但不自动改代码。
输出示例：“结算页价格卡片确定受影响（Page → Component → API Client → Field，代码引用 2 处，当前生产版本仍有流量）；订单列表可能受影响（历史方案提及但当前代码未发现引用）；建议先新增兼容字段并观察 7 天，再删除旧字段。”每条路径均可展开证据。

8.2 需求完整性评审

  1. 按需求类型加载 Checklist：状态机、角色权限、空/错/弱网态、幂等、数据口径、埋点、监控、灰度、回滚。
  2. 结构化检查字段是否存在；语义检查正文是否有实质描述，而非仅出现关键词。
  3. 召回相似需求和相关事故，指出以往遗漏造成的问题。
  4. 输出“缺失、含糊、冲突、已覆盖”四类结果，问题项附引用和建议补充文本。

8.3 线上故障排查

  1. 确定症状、环境、租户、时间窗口与 SLO；从异常指标定位服务和接口。
  2. 沿运行时 Trace 与静态依赖图扩展上下游，关联同期发布、实验、配置和 Schema 变化。
  3. 查询错误模板和日志样本，召回相似事故；建立按时间排序的证据时间线。
  4. 对假设逐一给出支持证据和反证，推荐验证步骤；高风险操作只生成 Runbook 并请求确认。

10. 置信度与证据机制

10.1 Evidence Envelope

每个证据项至少包含：source_type、source_uri、source_revision、fragment（页/段落/文件行/查询窗口）、content_hash、observed_at、valid_time、acl、extractor 与 assertion_type。

10.2 置信度不是模型自报概率

最终评分由可解释特征计算，模型只负责识别命题与组织语言：

confidence = calibration(
  source_reliability × 0.28 +
  evidence_directness × 0.22 +
  cross_source_agreement × 0.18 +
  freshness_and_version_match × 0.14 +
  entity_resolution_quality × 0.10 +
  runtime_validation × 0.08
) - conflict_penalty - permission_blindspot_penalty
区间展示行为
≥ 0.85高置信可给确定结论，同时保留证据与版本限定。
0.60—0.84中置信使用“很可能”，列出缺失验证项。
< 0.60低置信不包装成结论；展示假设并建议补充数据/人工确认。

置信度需要用标注集做校准（如 isotonic / Platt），分场景评估，不能用一个阈值覆盖影响分析与事故根因判断。

10.3 引用与冲突

  • 事实型句子必须绑定至少一个 Evidence ID；一条引用不应支撑超出其内容的结论。
  • 文档与代码冲突时同时展示，并按时间、环境和事实等级解释；不得静默选择。
  • 因权限不可见而无法完整分析时，显示“结果可能不完整”，但不泄露受限对象名称或数量。
  • 答案快照保存所用证据 ID、查询计划、工具版本、模型版本和提示模板版本，支持复现。

11. 权限、安全与治理

身份与授权

OIDC/SAML SSO；RBAC 管管理动作，ABAC 控制项目、业务线、环境、密级与数据域；查询以用户身份或受限服务身份执行。

数据隔离

所有记录携带 tenant/project/ACL；数据库 RLS + 应用层双重校验；检索前过滤，不依赖生成后脱敏。

密钥与加密

连接器凭证进入 Secret Manager；传输 TLS、存储加密、密钥轮换；日志禁止记录 token 与完整敏感正文。

提示注入防护

源文档视作不可信数据；内容与指令通道隔离；工具白名单、参数校验、最小权限和结果净化。

审计

记录谁在何时查询了什么范围、调用哪些工具、引用哪些证据、做过何种确认；审计日志不可变并有保留期。

知识治理

实体合并、关系纠错、来源优先级、过期策略和删除请求均有审批流；修正可回滚且不覆盖原始证据。

敏感场景门控

生产写操作、权限策略建议、涉及个人信息的跨源关联、自动创建/修改外部事项，均进入 human-in-the-loop。模型供应商配置支持自托管、零数据保留 API 和按数据等级路由。

11.1 业务线标签治理与防串线

  • 标签不是授权：即使用户主动选择某业务线，仍必须通过该业务线及底层数据对象的 ACL；错误标签不能扩大权限。
  • 候选不可泄密：作用域推断只在用户可见的业务线集合内返回名称；不得通过候选标签、计数或纠错信息暴露隐藏业务线。
  • 服务端强制过滤：Memory、Search、Graph、Code 和 Evidence 工具均接收不可省略的 effective_scope，由 Agent Runtime 签名传递；模型文本不能覆盖。
  • 全链路审计：记录本轮请求标签、有效标签、推断来源、用户修正、被排除记忆数量和各工具实际作用域。
  • 污染检测：离线扫描无标签记忆、异常 global 记忆、跨域摘要和标签漂移；发现后隔离而不是自动归并。
  • 删除与修正：用户可删除错误记忆或修正标签；修正产生新版本并异步清理旧索引，历史审计记录保留。

12.1 发行形态

ScaleDefault + ArangoDB/Neo4j + Qdrant + Kafka（按需）多团队、大图谱、高吞吐；ArangoDB 需单独核对许可证

提供 docker compose up 的默认路径和 Helm Chart 的生产路径；首次启动执行迁移、健康检查和示例项目导入。所有外部依赖均有 readiness probe、资源下限、备份恢复说明。

12.2 配置与模型中立

  • 通过环境变量/配置文件选择 LLM、Embedding、Reranker，提供 OpenAI-compatible adapter 与本地模型 adapter。
  • Connector SDK、领域 Schema、关系类型、Prompt/Evaluator 版本纳入仓库，避免核心能力锁在云服务。
  • 数据迁移工具支持导出实体、边、证据和索引 manifest；向量可重算，不作为不可迁移资产。
  • 默认关闭遥测；启用匿名遥测需明确 opt-in，不上传业务内容。

13.1 系统指标

采集延迟、解析失败率、索引 revision lag、实体重复率、孤立节点率、关系冲突率、查询 p50/p95、工具错误率、Token/模型成本、ACL 裁剪率和证据点击率。

13.2 Agent 质量指标

指标定义首期目标
Evidence precision引用是否真实支撑对应命题≥ 95%

Unsupported claim rate无证据事实陈述比例< 2%
Temporal correctness版本/时间点使用正确率≥ 95%
Permission leakage越权实体或内容泄露0

建立 Gold Set：真实需求影响链、已知事故根因、接口变更、完整性缺陷和权限边界。每次 Schema、解析器、检索、模型或 Prompt 变更均跑离线回归；线上采用影子流量与人工抽检。

14. 实施路线与待决策项

阶段目标验收出口
Phase 0：领域基线（2—3 周）统一实体/边/证据 Schema；Storage Port；评测集框架10 个手工标注链路可完整表达和回放
Phase 1：MVP（6—8 周）FastAPI + LangGraph 运行时；Git、OpenAPI、Jira/文档接入；PostgreSQL/pgvector；影响分析和需求审查单项目一键部署，支持流式回答与暂停恢复，答案具备行/段落级证据
Phase 2：运行时闭环（6—8 周）发布、日志/APM、监控、配置/实验；OpenSearch；排障链路可生成版本正确的故障时间线与验证步骤
Phase 3：规模化与生态专用图/向量适配、插件市场、多租户、Helm、治理工作台存储可替换，连接器 SDK 有兼容性测试

建议现在确认的技术决策

  1. 应用技术栈：默认采用 Python 3.12、FastAPI、LangGraph 和 Pydantic；FastAPI 与 LangGraph 通过应用服务边界协作，不让 HTTP DTO 或框架 State 侵入领域模型。
  2. 图存储起步：接受 PostgreSQL 关系图作为默认实现，同时从第一天定义 Graph Port；ArangoDB Community 作为可选 Adapter，不作为默认捆绑依赖，商业生产使用前核对许可证。
  3. 全文检索：默认版引入 OpenSearch；Lite 版允许 PostgreSQL FTS 降级。
  4. 向量检索：MVP 使用 pgvector，达到明确规模阈值再迁移 Qdrant/Milvus。
  5. 代码智能：首期聚焦 Java/Go/TypeScript/Python，使用 Tree-sitter + 符号/引用表；后续接入 SCIP。
  6. 事实政策：只有源系统事实、确定性解析结果或人工确认内容可进入 VERIFIED；模型抽取默认为 PROPOSED。
  7. 部署基线：Docker Compose 为社区快速开始，Helm 为生产推荐；默认不要求 Kubernetes。
架构结论：KnowItAll 应以“版本化知识图 + 多模态检索 + 证据驱动 Agent”为核心。RAG 是其中的语义召回能力，不是事实系统；Agent 是受权限和证据约束的查询计划执行器，不是直接对所有数据自由推理的聊天模型。
